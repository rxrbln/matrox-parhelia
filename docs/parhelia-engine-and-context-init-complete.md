**DMAPAD is generated by the accessor, not by the init code.** `[PARM]`
`0x11569`: if `dev->[0x54]` (posting-hazard tracking) is on and `0x114a3(dev,
reg)` says the previous register offset was within the hazard window, the
accessor first writes `mmio[0x384] = 0`, then records `dev->[0x58] = reg`, then
stores the value (`0x11543`, `0x1158e`). This is the same rule as `[KERN]`
`mtx3376` (kernel-abi §4.2). Every `0x384 = 0` in the traces is therefore a
side effect of the *next* write, and a re-implementation must apply the rule
generically rather than copy the pad writes from the trace.

## 1. Device / engine bring-up

### 1.1 The miniport hardware-init function `[PARM]`

Two copies exist, selected through a per-chip function table (no direct `call`
to either; both are reached via `[dev+0x4e44]`-style dispatch): `0x32b05`
(0x0527/0x0528 lineage) and `0x4cc02` (0x2539 lineage). Their MMIO content is
identical except where noted. Ordered, with the value or formula:

The 0x2539 copy additionally does `0x1c0c \|= 0x808`, `0x1c10 \|= 0x808`
(`0x4cf05`–`0x4cf32`) and, for 0x2539 rev 0 only, **`0x03a8 = read | 0x20`**
(`0x4cf6f`–`0x4cf7d`) — so the `0x3a8 |= 0x20` the X driver performs
unconditionally is, in the Windows stack, a 0x2539-only register write.

This is the same list `[XDRV]` `mtx1373` performs (`parhelia-engine-init.md`):
`0x8fc = 0`, `0x920 &= 0x7fffffff`, `0x10b0 = 0x40`, `0x12b8 = 0x70601`,
`0x12b0 = 0`, disarm 19, base block, `0x3a8 |= 0x20`. The Windows order puts
`0x12b8`/`0x12b0` *after* the heap construction and the `0x10b0 = 0x40` before
it; nothing in between touches the engine, so the two orders are equivalent.
**Neither copy programs the ring, the IRQ mask, `0x300`, `0x308` or `0x314`;
those belong to the bus-master arm (§1.3).**

### 1.2 Reset — the one path that clears a locked engine `[PARM]`

`0x33eec` (reached through the same dispatch table; `HSLPARHardwareReset` in
the Linux HAL, `parhelia-drm-design.md` §5.3):

```
0x33f12   0x322be(dev)            save 0x360/0x364 (0x2538/0x2539 only), 0xe20, 0xe2c
0x33f1d   ebx = 0xe0              PCI config offset of the strobe
0x33f28   cl = ((dev[0x3a8] & 0xe0) != 0x80)      -> save/restore 0xf4/0xf8 too
0x33f35.. save PCI cfg 0x04, 0x0c, 0x10, 0x14, 0x30, 0x3c, 0x40 [, 0xf4, 0xf8]
0x33fe1   if devid in {0x0528, 0x2537, 0x2538, 0x2539}: write 0x0308 = 3
0x33ff4   old300 = read 0x0300
0x33ff9   new300 = ((cfgF4 & 0x17) << 16) | ((cfgF4 & 0x1c00) << 11)
                 | ((cfgF8 >> 2) & 0x80000) | (cfgF4 & 0xff000000)
                 | (old300 & 0xffff)
0x3403d   write 0x0300 = new300 & ~0x100              <- bit 8 cleared
0x34046   PCI cfg[0xe0] = 3
0x3404f   PCI cfg[0xe0] = 0                            <- the strobe
0x3405a   delay 10000 us
0x34065.. restore PCI cfg 0x0c, 0x10, 0x14, 0x30, 0x3c, 0x40, 0x04 [, 0xf8]
0x340ce   write 0x0300 = new300                        <- bit 8 restored
0x340d4   0x32340(dev)            re-toggle PLLs 0xe20/0xe2c (write v|0x80000000, 100 us, write v); restore 0x360/0x364
```

So the disputed "which bit of `0x300` is cleared at step 3" in drm-design §5.3
is settled by this copy: **bit 8** (`and eax,0xfffffeff` at `0x34035`).
Everything above bit 15 of `0x300` is derived from the PCI-X capability
(`cfg 0xf4/0xf8`) and, per the hardware measurement in
`tools/parhelia-3dtri.c` (`probe_300`), reads back as zero on the PCI 0x0528 —
the high half is read-only status. What survives is the low 16 bits, held by
the vendor at `0x140` (§1.3).

After the strobe the miniport re-runs its init (§1.1) and the display driver
re-arms (§1.3). There is no lighter engine-only reset in any of the three
binaries: the `0x308 = 3` write alone is *part of* this sequence, not a
substitute for it. This answers §3's "anything short of a power cycle?": yes —
the config-space strobe, which the vendor Linux stack never calls but the
Windows miniport does.

### 1.3 Bus-master / ring arm `[PARD]` + `[KERN]` + `[HW]`

The Windows display driver's ring-restart, `0x328d0`, is instruction-for-
instruction the Linux `mtx2508` (kernel-abi §6.4):

```
0x328f9/0x32922  poll 0x08f0 until bit 17 (0x20000)          "primary DMA idle"
0x32954          (if the FIFO-tracking shadow says so) read 0x0000 == 0xffffffff? -> repeat
0x329af          ctx[0x503c] = ringBias | writePtr           (ring bus-address bias + kernel offset)
0x329c4          write 0x0404 = ctx[0x503c] & ~3             PRIMADDRESS
0x329ef          v = ring->[0x18]; if (caps->vtbl[0xc]() & 4) v &= ~0x1f
0x32a02          write 0x0400 = v
```

`[KERN]` `mtx2508` @0x31880: identical, with `0x450` polled to equality with
the boot snapshot in between (`0x31938`–`0x3194a`) and `0x400 = pStatus[0x40]`
(`0x319dd`), 32-byte aligned when capability bit 2 is set.

**What `0x400` is.** In the open trace `[HW]` the ring is at bus `0x14600000`
(`0x404 = 0x14600000`, doorbells `0x14600023, +0x20 …`) and `0x400 =
0x177ff000`. `0x177ff000 − 0x14600000 = 0x031ff000`, i.e. exactly one page
short of a 50 MB (`0x3200000`) region starting at the ring base. Together with
the Windows source (`ring->[0x18]`, the field next to the write pointer
`[0x1c]`, aligned down to 32 bytes) and kernel-abi's own label for
`pStatus[0x40]` ("ring limit value written to 0x400"), `0x400` is **the primary
ring's end/limit (bus address), the wrap point** — not a status write-back
page. `[INF]` for the wrap semantics; `[BIN]`+`[HW]` for the value. Consequence
for a driver: allocate the ring as one physically contiguous DMA32 block, write
its bus base (low 2 bits clear) to `0x404` and its end (bus, 32-byte aligned)
to `0x400`, and never let `0x408` pass `0x400`.

The complete open-time order, from `captures/mmio-draw-0528.txt` `[HW]` (the
only capture that begins before the arm; PIDs 21/22 are two opens by the X
server, the second one owns the engine):

```
 1  R 0x0450 -> 0xffffff8f          idle snapshot (the WaitBusMastering constant, see §3)
 2  W 0x10b0 = 0x00000010           bus-master arm value (0x40 was the X-init value, §1.1)
 3  W 0x12b8 = 0x00070601
 4  R 0x0300 -> 0x00000140
 5  W 0x0300 = 0x1f0b0140           = read | PCI-X-derived high bits; only the low 16 bits stick [HW]
 6  W 0x0384 = 0                    DMAPAD, generated by the accessor

    ... (second open repeats 1-7) ...

11  R 0x0450 -> 0xffffff8f          wait FIFO/idle snapshot    }
12  W 0x0404 = 0x14600000           PRIMADDRESS = ring base    }
13  W 0x0400 = 0x177ff000           ring limit                 }
14  W 0x0314 = 1  x8
15  W 0x0920 = 1                    WARP enable (bit 0)
16  W 0x0000 = 0x10000000, 0x0004 = 0, 0x0008 = 1, 0x000c = 0x10001     descriptor 0 (whole VRAM)
17  W 0x0010..0x0090 (+0x10) = 0    descriptors 1..9 disarmed (d0 only)

20  W 0x0130 = 0x1fe00000, 0x0134 = 0x08000000, 0x0138 = 1, 0x013c = 0x10001   descriptor 19
21  W 0x0920 = 1
22  W 0x0bc0 = 0x00004087           memory-config word (value from the capability vtable, §1.5)
```

and the teardown, symmetric: `0x0010 = 0`, `0x0020 = 0`, last doorbell, `0x08fc
= 0`, `0x0000 = 0`, all 19 others `= 0`.

Steps 8–15 and 21–24 are `[KERN]`: the kick (`0x314`) and `0xbc0` come from the
core (`mtx1475` @0x3e830 writes `0xbc0` with the return of `caps->vtbl[0x20]()`;
`0x8fc` from `mtx2070` @0x3af7f, §3), the ring from `mtx2508`; step 15/21 from
`mtx656`. Steps 16–20 and 25–26 are `mtx2521` (§1.4).

### 1.4 The descriptor bank `0x0000..0x013c` `[KERN]` + `[PARM]` + `[HW]`

Twenty 16-byte entries, index `i` at `i << 4`. The writer is `[KERN]`
`mtx2521(mgr, slot, u32 tail[3], u32 d0, bool)` @0x623b0: `slot += mgr[0xa0]`
(slot base), then, with the inline write-helper template (FIFO count at
`+0x8c/+0x90`, `0x450` bit 22 poll, hazard pad), writes

```
(slot<<4)+4  = tail[0]          (0x62405)
(slot<<4)+8  = tail[1]          (0x624f0)
(slot<<4)+c  = tail[2]          (0x625dc)
(slot<<4)+0  = d0 | 0x10000000  (0x626d1)     <- written LAST: bit 28 = valid/enable
```

The `bool` path (`0x627d0`) writes only `+0` with `d0 | 0x10000000`; the trace's
disable writes `+0 = 0` come from `mtx724` @0x62c00 (loop over slots, called from
the allocator `mtx3093`) — a slot is disabled by clearing bit 28, which is also
what the miniport's "disarm 19" loop and the self-test's `& 0xe0000000` mask
do (`0x56be3`).

`d0` is produced by the three registration sites identically:
`d0 = (offsetInObject + memobj[0x30]) | mgr[0xd8]` (`mtx236` @0x63c2a,
`mtx2965` @0x655b6, `mtx724` @0x62c5c), where `memobj[0x30]` is the object's
VRAM byte offset (the CPU maps `BAR0 + d0[27:0]` right after each registration
in the trace: `MAP 0xd0040000` for `0x10040000`, `MAP 0xd0ec0000` for
`0x10ec0000`, `MAP 0xd0f00000` for the per-draw `0x10f00000`) and `mgr[0xd8]`
carries the memory-type nibble (0 on the PCI board; the miniport self-test ORs
`BAR0 & 0x0e000000` into it at `0x56c34`, so bits 25–27 of d0 are a bus-address
component on boards whose BAR is not 256 MB-aligned `[INF]`).

`tail[0..2]` (d1, d2, d3) are *not* computed by the kernel: they are copied
from the registration record (`rbx+0x18..0x20` in `mtx236`, filled from the
ioctl/record payload) — the client describes the surface. Their format matches
the 2D surface words the same object builds elsewhere (`mtx3388` @0x500f2:
`bpp<<28 | 0x10000 | pitch` with 8/16/32 bpp = 1/2/3, `0x34000000` for the
`0x1e` format), so:

| dword | reading | evidence |
|---|---|---|
| d0 | `[28]` valid, `[27:0]` VRAM byte offset (or bus-address bits on non-aligned BARs) | `mtx2521`, MAP correlation `[HW]`, self-test `[PARM]` |
| d1 | second address. Observed: `0` (slot 0, 1), `0x07f60000` (slot 2), `0x08200000` (slot 10), `0x08000000` (slot 19), `0x018e8000`/`0x09002000` (slot 3, per draw), `0x08000000` (miniport self-test slot 0). Slots 19 and 10 are contiguous in this space (`0x08000000 + 0x200000 = 0x08200000`, and slot 19's VRAM region is exactly 2 MB) — a GPU-linear window base `[INF]`; the per-draw values are page-aligned system addresses `[INF]` | `[HW]` |
| d2 | `bpp<<28 \| flags<<16 \| pitch`: `0x30030780` = 32 bpp, flags 3, pitch 1920; `0x05000020`; `0x32030020`/`0x32030010`; `1` for linear heaps; Windows uses `0x10000020` for slot 0 and `0x10000400` for the self-test ring window | `[HW]`, `[PARM]` 0x32f15/0x56c57, `mtx3388` format rule |
| d3 | `height<<16 \| width`-shaped: `0x10001` for linear/unbounded, `0x10708` for X's 1920-pitch surface, `0x10020` for the per-draw slot | `[HW]`, `mtx1399` @0xde09 writes the same `0x10001` into a surface record |

What the bank is for `[INF]`: a table of twenty *surface windows* the engine
resolves addresses through. Slot 0 is the whole VRAM (identity), slots 10 and
19 are the two kernel heaps allocated at open (126 MB at VRAM `0x7fc0000`, 2 MB
at `0xfe00000` — the `MAP 0xd7fc0000/0xdfe00000` regions), slot 1 is the X
server's render surface, slot 2 a 14 KB VRAM buffer, slot 3 is re-programmed
before each of the ICD's uploads (`mmio-gltri` shows `0x030 = 0`, doorbell,
`0x030..0x03c = {0x10f00000, busAddr, 0x3203xxxx, 0x1002x}`, a 4 KB CPU map of
VRAM `0xf00000`, then `0x030 = 0` again — a staging window through which a
system-memory page is pulled into VRAM). This is the strongest candidate for
the space-class-2 resolution in `parhelia-3d-submission-audit.md` D.1: an
`offset|2` address is relative to the currently armed pull window, whose bus
side is d1. The experiment is in §6.

The miniport's own descriptor writes are the base block only (§1.1 rows 18–22);
per-heap registration on Windows happens in the display driver through the
queued writer (`0x91840`), which is why no other `0x0000..0x013c` immediate
exists in `MTXPARM.sys`.

### 1.6 Allocation requirements `[BIN]` + `[HW]`

* Primary ring: physically contiguous, DMA32, bus address written to `0x404`
  (low 2 bits clear) and its limit to `0x400`; the doorbell `0x408` carries
  `bus | 3` for a system-memory ring (`endFlags` from the buffer's space word,
  kernel-abi §6.1). The vendor reserves `0x14` bytes per submit and pads to
  `0x20` (`[PARD]` `0x32c50` pads with `0x21212121` up to the alignment in
  `ctx[0x74]` = 0/8/16 dwords depending on `[0x158]`).
* Status page for the write-back fence: the ICD's `0x1090/0x1094` packet
  targets a one-page PCI_LOCKED buffer (kernel-abi §3.3: two DMA-visible pages
  per link). Nothing in the arm registers points at it; it is addressed only
  from the stream.
* Windows self-test buffers (`[PARM]` `0x56ef1`): primary ring at VRAM 0, size

## 2. GL / D3D context creation

### 2.1 What happens at link/context creation `[KERN]` + `[PARD]`

Linux: `ioctl 0xc038461f` → `mtx1775` allocates the link object and three
one-page buffers (kernel-abi §3.3) — **no MMIO**. The first RENDER of the new
context runs the validators and `mtx3400`, and `mtx3806` performs the canned
burst (below). Windows: D3D context creation (`0x7c8a0`) calls `0x7a540(1)`,
then `0x7c770` (the canned burst), then writes `0x920` (`0x7c8d8`) — the same
shape.

### 2.2 The instruction loader — `[KERN]` `mtx1391` @0x9f6b0 = `[PARD]` `0x7b850`

Read out of the Windows copy (unobfuscated field use), matching the Linux one
field for field:

```
Load(this, bReset, prog, entryIdx):
  if bReset: this[0x57740] = 0 (byte cursor), this[0x5774c] = 0 (overflow flag)
  if this[0x57740] + prog[0x24] >= 0x1800: this[0x5774c] = 1; return 0     <- 6144-byte store = 512 instructions
  0x2bef0(...)                       lock
  0x7a910(dev)                       WARP idle gate (§3)
  write 0x0918 = cursor / 12         <- instruction index (0xaaaaaaab mul, >>3 = /12)
  for i in 0 .. prog[0x24]/12:       write 0x091c = w0, w1, w2   (three dwords per instruction, prog[0x28] is the dword pointer)
  cursor += prog[0x24]
  return (cursorBefore/12)*4 + 4*prog[0x30 + entryIdx*4]
```

So **the entry value is `4 × (instruction index + per-variant entry offset)`**;
it is always a multiple of 4. A value such as `0x08a57183` is not an entry —
its low two bits are set — and no producer in the four binaries yields one:
`mtx1391`/`0x7b850` return `4*n`, the "unbound" placeholder is `2`, and the
`0x1100` writes carry exactly those. Dwords of that shape belong to the
instruction stream itself (`w0` of an instruction; the vertex-ISA word layout
is in `parhelia-vertex-isa.md`). Treat any "packed store index" reading of
such values as unsupported `[INF, negative]`.

writes `0x920 = 0x80000000` then `0` (`0x56c81`–`0x56c91`) before running the

(`0x56a15`–`0x56b6f`: `0x910 = (x & 0xf1fcf000) | 0x1000000`, `0x938 = -4`,

and the result is fetched through the port; during rendering the vendor writes
`0x920 = 1` (`[HW]` steps 15/21). Bit 0 therefore selects where the WARP's
output goes — the setup unit (1) or the readback port (0) `[INF]`; bit 31
strobed high-then-low resets the unit `[INF]`. This is the reason
`parhelia-warp-readback.md`'s readback reads never reflect a draw: the port
is only fed when bit 0 is clear.

## 3. Interrupts and status

### 3.1 ISR `[PARM]` `0x111f0` = `[KERN]` `mtx1415` @0x3adb0

```
status = read 0x08f4;  if 0 or 0xffffffff: not ours
[KERN] write 0x08f8 = status                       (ack everything at once, 0x3ae21)
[PARM] per source, ack by writing the bit to 0x08f8, then dispatch:
   0x00040000  -> 0x17077 acks, event 5
   0x00010000  -> 0x1708d acks, event 6
   0x00020000  -> 0x170a3 acks, event 7
   0x00000001  -> 0x170b9 acks, event 0, then reads 0x1924 (head-0 status, bit 0x2000000)
   0x00000002  -> 0x170df acks, event 2, then reads 0x1b24 (head-1 status)
   0x00000010  -> vblank: enable = write 0x8f8 = 0x10 then 0x8fc |= 0x10 (0x16fe9..0x16ffe); disable = 0x8fc &= ~0x10, 0x8f8 = 0x10
```

Only bits that are also set in the enable shadow (`dev[0x50]`, the value last
written to `0x8fc`) are dispatched. `[KERN]` `mtx2070` recomputes `0x8fc` as
the OR of every enabled handler slot's mask (`0x3af2a`–`0x3af7f`, five slots of
`0x78` bytes at `dev+0x68/+0x70`). The Linux open enables exactly `0x10000`
(`[HW]` step 24) — bit 16, "event 6". Which engine event that is (soft-trap /
DWGSYNC-tag completion, or primary-DMA end) is not named in any binary string;
given that it is enabled right after the ring goes live and that the
blocking DWGSYNC form is the only thing that never completes without the
vendor init, bit 16 = the SOFTRAP/DWGSYNC interrupt is the working hypothesis
`[INF]`; bit 18 (`0x40000`, event 5, also `mtx3282` step 12's mask) is the
other engine source.

**WaitBusMastering** (`[PARM]` `0x56f4a`): poll `0x8f0` bit 17, then poll
`0x450 == constant`. **WaitWarpIdle** (`[PARM]` `0x57020`): WaitBusMastering,

`0x918`.

### 3.3 The latched `0x03020000` / `0x02020000` states

`0x8f0 = 0x03020000` = primary DMA idle (bit 17) **and** both WARP-busy bits;
`0x02020000` = idle and one WARP-busy bit. Both mean "the ring drained but the
WARP never came back". Nothing in the three binaries clears bits 24/25 by a
register write: the loader refuses to stream while they are set, the ring
restart does not look at them, and the only path that returns them to zero is
the chip reset of §1.2 (config-space `0xe0` strobe, followed by the full
re-init). The self-test's `0x920 = 0x80000000 → 0` strobe (`[PARM]`) is the
one WARP-local reset gesture in the binaries; whether it clears a stuck
busy pair is untested `[OPEN]` and is the cheapest experiment in §6.

## 6. Open items, each with the experiment that closes it

1. **`0x400` = limit.** Program `0x400 = ringBus + ringSize − 0x1000` and
   submit a 2D fill whose packet straddles that address; a wrap (fetch pointer
   returning to `0x404`'s value) confirms it, a stall refutes it.
2. **Bit 16 of `0x8fc` and the blocking DWGSYNC.** Phase 2 in full (including
   2.6–2.9 and 2.15) followed by `tag|1` behind a 2D fill; `0x41c == tag` and
   `0x8f4` showing bit 16 (ack with `0x8f8`) settles both the bit name and
   audit D.4.
3. **Slot 3 as the class-2 window.** Program `0x030..0x03c = {0x10f00000,
   busOfSecondaryBuffer, 0x32030020, 0x10020}`, then issue the secondary call
   with `SECADDRESS = offset|2` (offset relative to that buffer). If it
   executes, audit D.1/D.5 are closed and the vendor's per-draw stream can be
   replayed literally.
4. **`0x920` bit 0 = output routing.** Run the miniport self-test packet set
   (§2.4) with `0x920 = 0` and read the port; then the same with `0x920 = 1`
   and read VRAM. Only one of the two should see the result.
5. **`0x920 = 0x80000000 → 0` as a WARP-local reset.** On a board reading
   `0x8f0 = 0x03000000`, apply the strobe and re-read; if bits 24/25 clear,
   the config-space reset is not needed for the common failure.
6. **d1 of the descriptor bank.** Register slot 19 with `d1 = 0x08000000` and
   slot 10 with `d1 = 0x08200000` as the vendor does, then reference a VRAM
   object through `offset|2` vs `offset|3`; whichever class resolves through
   d1 identifies the space it defines.

None of the above has been run on the 0x0528 host in this pass.
