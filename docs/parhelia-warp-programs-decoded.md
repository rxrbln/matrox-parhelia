# Parhelia WARP — the vendor's live programs, decoded; our generated replacements

The class-3 program heap of a working flat-shaded triangle on the original
Parhelia-512 (0x0528) was read out of RAM while the vendor kernel was running
(`captures/live-ring-0528/warp-programs/slot-*.txt`, eight 0x600-byte slots of
128 instructions; `entries.txt` = the entry values the same draw wrote to the
WARP registers).  This document decodes every slot with the dual-issue ISA of
`docs/parhelia-warp-isa-complete.md`, says what each program is, corrects the
ISA document where the hardware data disagrees with it, and gives the exact
dword lists of programs generated by our own assembler that can be bound in
place of the vendor's.

Tags: **[HW]** read out of the live dump / ring capture of this draw;
**[BIN]** read out of a vendor binary (`mtx_parhelia.o` by ELF symbol,
`MTXPARD.dll` as quoted by the ISA doc); **[INF]** inferred; **[OPEN]** not
established.  No proprietary C source was read.

Tools written for this document:

* `tools/parhelia-warpdis2.py` — decoder.  `python3 tools/parhelia-warpdis2.py
  slot.txt -f -E 96` (fold pads, mark entry), `--elf mtx_parhelia.o --sym
  mtx1621` (decode a `.data` blob), `-s` stop at END.  Prints one readable
  line per bundle and a flag column for every field whose meaning is not
  settled.
* `tools/parhelia-warpasm.py` — assembler / generator.  `--gen transform
  --matrix a0 --tex 4 --vs slot-16c06200.txt --vs-entry 96` regenerates the
  vendor's live program and compares it bit for bit; `--gen passthrough`,
  `--gen transform`, `--tex N`, `--colour vN`, `-o file.hex`, `--c-array NAME`.

## 0. Headline

1. **The per-vertex program the vendor binds for this draw is the 13-bundle
   fixed-function program `0x50 + 0x54 + 0x4d + 0xc8`** predicted by
   `docs/parhelia-warp-codegen.md` §4.3, byte for byte [HW == BIN].  It lives
   at slot `16c06200` index 96 and is the value written to `0x1100` with
   MODE `0x20000002`.  Decoded (§3):
   `add T0←v0`; four `dp4 r2.{w,z,y,x} ← T0 · c[a0.x+3..0]` each paired with a
   texcoord move `o3..o6 ← v7..v10`; `add o1 ← v5 | mov T1 ← c[b1+1]`;
   `smul r5 ← r2, r2.xyz1 | mov o11 ← r2`; `add o2 ← v6`; then the output
   tail `add T1.xy ← T1 + c[b1+8].ww`, `mad T1.xyz ← c[b1+0].xyz1·r5 + T1`,
   `sub o0 ← T1 − c[b1+8].ww00 | sop2 r5.w ← r5`; `end`.
2. **The position reaches the rasteriser as `o0` in window pixels**, not clip
   space: `r2` = clip position, `r5` = `r2 / r2.w` (op 0x89), `T1` = viewport
   offset `c[0x161]` + snap constant, `o0 = c[0x160].xyz · r5.xyz + T1 − snap`.
   `o0.w` is `c[0x161].w` (= 240.0 in this draw).  [HW dataflow, INF for the
   op-0x89 divide]
3. **Base registers of this draw: `b0 = 0x0e0`, `b1 = 0x160`, `b2 = 0x080`,
   `b3 = 0x800`; the program index register `a0 = (0,1,2,3)`.**  They are
   *not* hidden state: the vendor sets them by binding and running three small
   canned programs (kinds 3, 0, 1) whose input vectors are the block-load
   packets that follow each bind.  The sub-header dwords `e0 160 80 800` of the
   kind-1 packet are the four bases; `0 1 2 3` is `a0`.  [HW packet contents,
   INF that the programs' `mova`/`ctl33` writes are what installs them]
4. **Our assembler reproduces the vendor's live program bit for bit** (13/13
   words) from mnemonic text, reproduces the ISA doc's D3D-assembler words and
   16 further kernel fragment words (extended indices, negation, three-source
   `mad`, paired secondaries).  Generated programs and the exact binding values
   are in §7–§8.
5. **Corrections to the ISA doc** (§2): the "arithmetic ⇒ `f2b=1`" rule is
   wrong (every clipper/stage program is arithmetic with `f2b=0`); the kernel's
   proven src1-relative encoding uses `f1g=0` where the D3D assembler leaves 1;
   `extsel=1` with `exthi=0` is a second inert value; `w1[21:20]=1` accompanies
   the tail's two src1-relative `c[b1+8]` reads; the vendor transform reads the
   position through latch `T0`, never `v0` directly; `base0` is `0xe0` (so
   `c[b0+105]` is the projection at `0x149`, not "palette entry 105");
   the stage-entry registers `0x10c8..0x10d8` do **not** all carry the
   generated program's entry on this hardware path.

## 1. The eight slots and what they are

`entry` is the value written to the register; bus = `(entry & ~3) * 3`
(the entry is `4 × instruction index`, instruction index = bus address / 12,
so **the WARP fetches instructions from system memory** on this path)
[HW arithmetic, matches the loader formula of `parhelia-warp-binding.md` §2].
Index inside the slot = `(bus − slotbase) / 12`.  All linker outputs start at
index 96 = 128 − 32 because the linker prepends pad so the last fragment begins
on a 32-instruction boundary (`parhelia-warp-codegen.md` §3.7) [BIN, HW].

|---|---|---|---|---|---|---|
| `16c05000` | `07957183` | 96 | `mtx1824` = kind 3, 17 instr, byte-identical [HW=BIN] | control, `f2b=0` | 1st `0x1100`, MODE `0x20000028` | installs the resident-program entry pointers from its input block (§4.1) |
| `16c05600` | `07957383` | 96 | `mtx1079` = kind 0, 14 instr [HW=BIN] | control+`mova` | 2nd `0x1100`, MODE `0x20000028` | the **constant-file loader**: copies the following block loads into `c[]` with `a0` stepping (§4.2) |
| `16c05c00` | `07957583` | 96 | `mtx251` = kind 1, 29 instr [HW=BIN] | control+`mova` | 3rd `0x1100`, MODE `0x20000028` | installs base registers `b0..b3`, `a0`, control words (§4.3) |
| `16c06200` | `07957783` | 96 | generated `0x50+0x54+0x4d+0xc8`, 13 instr [HW=BIN] | **vertex, `f2b=1`** | 4th `0x1100`, MODE `0x20000002`, `0x10f8=2` | **the per-vertex transform / colour / texcoord / tail program** (§3) |

words differ — a previous allocation, not part of this draw) [HW].

exactly the `mtx3400` condition for skipping `S[0x80]` [HW, consistent with BIN].

The coordinator's first reading of the stage entries ("index 15 / 19") was an
arithmetic slip: `0x16c06d34 − 0x16c06800 = 0x534 = 111 × 12`,
`0x16c06d64 − 0x16c06800 = 0x564 = 115 × 12` [HW].

## 3. The per-vertex program (slot `16c06200`, entry 96) — decoded [HW]

```
  96: 00003e00 00440000 b89a2249 | add T0, v0, v0.0000
  97: 1874a23f 28022303 bb9a21a2 | dp4 r2.w, T0, c[a0.x+3] | mov o3, v7    ; f1g=0 extsel=1
  98: 1084924f 28022303 bb9a21a2 | dp4 r2.z, T0, c[a0.x+2] | mov o4, v8
  99: 08948a5f 28022303 bb9a21a2 | dp4 r2.y, T0, c[a0.x+1] | mov o5, v9
 100: 00a4866f 28022303 bb9a21a2 | dp4 r2.x, T0, c[a0.x+0] | mov o6, v10
 101: 0e187c1f 32440215 b89a2249 | add o1, v5, r1.0000     | mov T1, c[b1+1]
 102: 12257ebf 00440289 c49a22a2 | smul r5, r2, r2.xyz1    | mov o11, r2
 103: 0808be00 00440019 b89a2249 | add o2, v6, r1.0000
 104: 40004e00 ea540107 b89a2246 | add T1.xy, T1, c[b1+8].ww00              ; w1[21:20]=1
 105: 2c105e00 22440181 bb6a2222 | mad T1.xyz, c[b1+0].xyz1, r5, T1.xyz0
 106: 42583d58 ea540507 b99a2246 | sub o0, T1, c[b1+8].ww00 | sop2 r5.w, r5 ; w1[21:20]=1
 107: 00000200 00040000 14c00000 | end
 108: 00080200 00440000 301a21a2 | wra (pad, f2b=0)
```

Fragment boundaries [BIN]: 96–100 = registry `0x50` (`mtx1621`) with the four
`dst1` patches `3 → 2`; 101–103 = `0x54` (`mtx737`); 104–106 = `0x4d`
(`mtx3888`); 107–108 = `0xc8`.

### 3.1 Roles

* **Transform (96–100).**  `T0 = v0` (the fetched position, `[x y z w]` floats
  with `w = 1.0`, descriptor `0x10b8 = 0x20c00000`), then `r2.c = T0 · M[c]`
  with the matrix rows at `c[a0.x + 0..3]`, `a0.x = 0` (§4.3) → block entries
  `0x000..0x003`, which for this draw hold the fused 320×240 ortho MVP
  `(2/320, 0, 0, −1) / (0, 2/240, 0, −1) / (0, 0, −1, 0) / (0, 0, 0, 1)` [HW].
  The same four rows are loaded again at `0x149..0x14c` (the projection slot);
  the program reads the copy at 0 [HW].
* **Texcoord outputs (secondary halves of 97–100).**  `o3..o6 ← v7..v10`
  unconditionally, even with no texture bound (the inputs are the default
  attribute vector) [HW].  This is the `0x50` fragment's built-in pairing; the
  ISA doc's `0x18a460` texgen epilogue is the D3D equivalent.
* **Colour (101, 103).**  `o1 = v5 + 0` (primary colour, descriptor
  `0xa1c50020`: 3 components at dword 2, slot 5 — the `[x y z w c]` stream's
  5th float and the two after it), `o2 = v6 + 0` (secondary colour, unbound →
  default vector).  The `+ r1.0000` is the library's way of writing a move with
  the primary ALU; `r1` is uninitialised scratch and contributes nothing
  because the swizzle selects the constant 0.0 [HW].
* **Address latch (secondary of 101).**  `T1 ← c[b1+1]` = `0x161` = viewport
  offset `(160, 120, 0.5, 240)` [HW].  `T1` is also the D3D `a0`; a plain `mov`
  (secondary op 1) to `T1` does **not** disturb the `a0` the `dp4`s use, since
  the transform of the *next* vertex still reads `c[0..3]` — so the address
  latch is written only by `mova` (op 9) [INF, strong].
* **Divide + clip copy (102).**  `r5 = op89(r2, r2.xyz1)`; the ISA doc's
  family `0x8a = s1 × rsq(s0.w)`, `0x8b..0x8d` scalar on `.w` makes `0x89 =
  s1 × rcp(s0.w)` → `r5 = (x/w, y/w, z/w, 1/w)` [INF, strong].  `o11 ← r2`
  keeps the clip-space position for the clipper stages [INF].
* **Viewport tail (104–106).**  `T1.xy += c[0x168].ww`; `T1.xyz = c[0x160].xyz
  · r5.xyz + T1.xyz` with `c[0x160] = (160, −120, 0.5, 1)` = `(W/2, −H/2,
  depth scale)` — the Y flip is in the constant; `o0 = T1 − c[0x168].ww00`.
  `0x168` is not loaded by this draw, so on this hardware it is whatever the
  context left there — the shape (add then subtract the same `.w`) is the
  float-to-fixed grid snap that `0x178.w = 786432.0 = 1.5·2^19` is built for
  [INF].  `o0.w = T1.w = c[0x161].w = 240.0` [HW].
* **`sop2 r5.w ← r5` (secondary of 106).**  Writes only `r5.w`; nothing reads
  it afterwards.  Either a dead write or a side effect of secondary op 2 (an
  `rcp` of the `1/w` back to `w`, or a rasteriser latch).  [OPEN]

## 4. The three standalone programs and their packets [HW]

Each is bound with `[4][403c3cdd][x][20000028][20000028][entry]` and followed by
one `0x41` packet whose 4 sub-header dwords + N vec4 are the program's `v0..`
inputs [HW order; the assignment of sub-header = `v0`, data = `v1..` is INF].
MODE nibble 8 = "run once on the following packet" [INF].

### 4.1 Kind 3 — `mtx1824`, entry pointers

```
 96: ctl33 (00040000)
 97: mov T0, v0.yyyy     98: mov T1, v0.zzzz     99: mov T2, v0.wwww
100: mov T3, v1.yyyy    101: mov T4, v1.zzzz    102: mov T5, v1.wwww
103: ctl0d imm=-1  104: nop
105..109: ctl33 with operands T2, v1?, T3, T4, T5 and src2 = 1..5   ; push latches to hw
110: op6e (f2b=0)   111: end
```
Packet: `41020007 | 03800015 00000000 3f800000 07956183 | 3f803f80 07955583 ffffffff 07956b83`.
With `v0` = sub-header, `v1` = data: `T0 = 0`, `T1 = 1.0f`, `T2 = 07956183`
(kind 12 entry), `T3 = 07955583` (kind 6 entry), `T4 = −1`, `T5 = 07956b83`
(stage-6 entry).  The program therefore installs the addresses of the resident
programs into hardware latches through `ctl33` [HW data, INF semantics].

### 4.2 Kind 0 — `mtx1079`, the constant-file loader

```
 96: sop8 r3                     ; save a0 -> r3 (sop8 = "write dst without source") [INF]
 97: ctl33
 98: mova T1.x, v0.yyyy          ; a0.x = v0.y = block index (first)
 99: mova T1.y, v0.zzzz          ; a0.y = v0.z
100: ctl42 imm=1  101: br -> 107 (loop exit test)  102: nop
103: mov c0, v0   {relative a0.x, dst file 3 = constant file}   ; c[a0.x] = v0
104: sop8 T1.xy                  ; a0 += 1 [INF]
105: br -> 100                   ; loop
106: nop
107: mova T1, r3                 ; restore a0
108: end
```
It is followed by the ordinary `[41..][count first 1 0][count × vec4]` loads
(8 @ 0, 5 @ 0x134, 5 @ 0x149, 5 @ 0x155, 2 @ 0x160, 4 @ 0x172, 1 @ 0x178,
2 @ 0x17d) — the sub-header `(count, first, 1, 0)` is exactly the `v0` this
loop consumes (`v0.y = first`).  **The block file is written by microcode,
through destination file 3.** [HW+INF]

### 4.3 Kind 1 — `mtx251`, base registers

```
 96..99 : mov T5,T4,T3,T2 <- v3.x,y,z,w
100..101: mov T1 <- v2.x ; mov T0 <- v2.y
102..105: mova T0,T2,T4,T6 <- v0        (address latches)
106..109: mova T1,T3,T5,T7 <- v1
110..115: ctl33 ×6 (operands T5..T0, src2 0x18..0x1d)
116..121: ctl35 ×6 imm 0xe8..0xfc
122: ctl05   123: end
```
Packet: `4106000f | 000000e0 00000160 00000080 00000800 | 00000000 00000001
00000002 00000003 | 02003004 0200300c 00000000 00000000 | 07955583 ffffffff
ffffffff ffffffff`.
`v0 = (0xe0, 0x160, 0x80, 0x800)` → `mova T0/T2/T4/T6` = **base registers
b0..b3**; `v1 = (0,1,2,3)` → `mova T1` = **`a0 = (0,1,2,3)`**, which is why the
vertex program's `c[a0.x+k]` reads block `0..3`; `v2.y = 0200300c` is the
`0x1130` control word; `v3.x` = the kind-6 entry again.  [HW data; the
base-register identification is INF but every kernel `c[b0+k]` / `c[b1+k]`
reference then lands on its documented block-map entry (§2), and `b2 = 128` is
what the D3D path requires.]

Consequence for our driver: **replay these three programs and packets
verbatim**, substituting our own entry values in the kind-3 and kind-1
packets, and `a0`/bases stay as the vendor's.  Nothing else in the capture
programs the base registers.

## 5. The resident and stage programs (`f2b = 0` class) [HW+BIN]

Kind 6 (`mtx3605`), kind 12 (`mtx2068`), and the linker-built stage programs
(`mtx2817`+`mtx2648`, `mtx847`) are a different instruction class: every
operand is base-relative (`T[b0+11]`, `c[b1+8]`, `o[b3+1]`), `f2b = 0`, and the
shapes are a clipper's — `sub c[b1+8] ← c[b1+8] − T1` (Δ = B − A), `smul r12 ←
T0, r12` (t = d/Δd), `mad o[b1+1] ← r12 · c[b1+8] + T1` (A + t·Δ), `movsat
o[b3+k] ← Tk` (copy attributes), then `sub o[b1+0] ← T1 − c[b1+24].ww00` (the
same snap as the vertex tail).  Decoded heads are produced by
`parhelia-warpdis2.py --elf … --sym mtx3605` etc.; they are not needed to bind
our own vertex program, and their control opcodes (`0x0d 0x25 0x27 0x2b 0x33
0x34 0x35 0x41 0x42 0x43 0x44 0x05`) with operand bits in `w0/w1` remain
[OPEN].  The decoder prints those operand bits as `ctl_operands=`.

Stage slot `16c06800`: entries 111 (`mtx2817` instr 0: `nop; ctl41 0x300; br
→118`) and 115 (`mtx2817` instr 4: `nop; ctl41 0x400; ctl41 4`) converge at 118
(`ctl0d 0x3800000; nop; mtx2648: ctl34 ×4, ctl35 ×4`).  This is the `mtx2884`
variant-2/3 vs 4/5 split of `parhelia-warp-codegen.md` §3.7 realised as two
entry offsets into one fragment [HW=BIN].

## 6. Generated programs (assembler output) and their validation

All words below are produced by `tools/parhelia-warpasm.py`, decoded back by
`tools/parhelia-warpdis2.py` (round-trip printed by the tool), and — where the
semantics coincide — compared against the vendor's live words.

### 6.1 Vendor program regenerated: `--gen transform --matrix a0 --tex 4`

13/13 words **IDENTICAL** to slot `16c06200` @96 (the tool's `--vs` output).
This is the encoder proof: every field the vendor program uses is produced
from mnemonics by the §2.1 routines plus two kernel conventions (`f1g=0` on
src1-relative — the default; `{extsel=1}` and `{f1g=1,u2120=1}` overrides on the
bundles that carry them).

### 6.2 (a) Screen-space pass-through: `--gen passthrough`

```
add o0, v0, v0.0000                  ; 00083e00 00440000 b89a2249
add o1, v5, r1.0000 | mov o11, v0    ; 08087ebf 00440215 b89a2249
end                                  ; 00000200 00040000 14c00000
wra                                  ; 00080200 00440000 301a21a2
```
Input `[x y z w]` in window pixels, `w = 1.0` (what this draw streams anyway),
colour in `v5`.  Field-by-field against the vendor where semantics coincide:

| ours | vendor | differing fields | why |
|---|---|---|---|
| `add o0 ← v0 + 0` `00083e00 00440000 b89a2249` | `add T0 ← v0 + 0` `00003e00 00440000 b89a2249` | only `fileB` 2 vs 0 (`w0[19:18]`) | we deliver to the output slot; the vendor parks the position in the latch for its `dp4`s |
| `add o1 ← v5 + r1.0000` primary half `08087e..` / `..15 b89a2249` | `0e187c1f 32440215 b89a2249` primary half | none in the primary fields (`dstB o1`, `src0 v5`, `src1 r1`, shared swizzle `0000`, op `0x71`) | identical operation |
| secondary `mov o11 ← v0` (`dstA=o11`, `src2=v0`) | secondary `mov T1 ← c[b1+1]` (`dstA=T1`, `src2=c1` base1-relative: `f1i=6`, `relcomp=1`) | `wmaskA/dstA/fileA`, `src2/file2`, `f1i`, `relcomp` | the vendor loads the viewport offset into `T1` here; we need no tail, and copy the clip position to `o11` as the vendor does one bundle later (`smul … \| mov o11 ← r2`, whose secondary half is bit-identical to ours apart from `src2 = v0` vs `r2`) |

The vendor's `o0.w` is `c[0x161].w` (240.0); ours is the stream's `w`.  If the
rasteriser needs the vendor's value, `--viewport-w` adds
`add o0.w, c[b1+1].wwww, v0.0000` = `00082200 22440184 b89b6e49` (needs `b1 =
0x160`, i.e. the kind-1 replay of §4.3).  Which one the setup unit wants is
[OPEN] — it is the first thing to test.

### 6.3 (b) 4×dp4 transform + colour: `--gen transform`

```
add T0, v0, v0.0000                              ; 00003e00 00440000 b89a2249
dp4 r2.w, T0, c3                                 ; 1804a200 00440103 bb9a21a2
dp4 r2.z, T0, c2                                 ; 10049200 00440103 bb9a21a2
dp4 r2.y, T0, c1                                 ; 08048a00 00440103 bb9a21a2
dp4 r2.x, T0, c0                                 ; 00048600 00440103 bb9a21a2
add o1, v5, r1.0000 | mov T1, c[b1+1]            ; 0e187c1f 32440215 b89a2249
smul r5, r2, r2.xyz1 | mov o11, r2               ; 12257ebf 00440289 c49a22a2
add o2, v6, r1.0000                              ; 0808be00 00440019 b89a2249
add T1.xy, T1, c[b1+8].ww00 {f1g=1,u2120=1}      ; 40004e00 ea540107 b89a2246
mad T1.xyz, c[b1+0].xyz1, r5, T1.xyz0            ; 2c105e00 22440181 bb6a2222
sub o0, T1, c[b1+8].ww00 | sop2 r5.w, r5 {f1g=1,u2120=1} ; 42583d58 ea540507 b99a2246
end                                              ; 00000200 00040000 14c00000
wra                                              ; 00080200 00440000 301a21a2
```
9 of 13 words identical to the vendor's; the four `dp4`s differ **only** in
`src1` addressing and the dropped texcoord secondary: `idxsel 0/1`, `f1i 0/5`,
`f1g 1/0`, `extsel 2/1` (absolute `c3` vs `c[a0.x+3]`), and `sop 0/1`,
`wmaskA 0/15`, `dstA 0/3..6`, `src2 0/7..10` (no `mov o3..6 ← v7..10`).  The
constants are the same as the vendor's: matrix rows at block `0..3` (`a0.x = 0`
makes the vendor's relative form read the same entries), viewport at
`0x160/0x161`, snap at `0x168`.  Requires `b1 = 0x160` (§4.3).  `--no-snap`
replaces the two `c[b1+8]` bundles by `add o0, T1, r1.0000`.

### 6.4 (c) transform + texcoord: `--gen transform --tex N`

Same as (b) with `mov o(3+i) ← v(7+i)` paired into the first `N` `dp4`s, e.g.
`--tex 1` turns bundle 1 into `1874a23f 00440303 bb9a21a2` = `dp4 r2.w, T0, c3 |
mov o3, v7` (vendor: `1874a23f 28022303 bb9a21a2`; only the relative-addressing
fields differ).  `--tex 4` with `--matrix a0` is the vendor program itself.

Cross-checks also run: the ISA doc §6.1/§6.2 D3D words (`00078600 00440003
bb9a21a2` … `0018021f 00440200 b01a21a2`, `00080600…`, `000801ef…`,

(`c[b0+105]`, extended index), `mtx1844`, `mtx270` (negated relative source,
`floor`), `AddAfs` (three-source `mad`), `mtx3945` — 16 words, all identical.

`E_x = 4 × (bus_address_of_first_instruction / 12)`, low two bits 3 on every
entry this driver writes (`…83`, `…bf`, `…cf`) [HW]; `2` = unbound.  For our
program: place the 4 (pass-through) or 13 (transform) words in bus memory,
`E_vertex = bus/3 | 3`, and keep every other value.  The kind-3 and kind-1
packets carry `E_kind6`, `E_kind12`, `E_stage6` — copy the vendor blobs
(`mtx3605`, `mtx2068`, and the stage slots) to memory too and fill those in, or
leave the vendor's own values if the vendor heap is still resident.

The constants our transform program needs, minimum: block `0..3` (matrix
rows, `dp4` reads row k for output component k), `0x160`, `0x161`, and
`0x168` (snap; unwritten = 0 = no snap), plus whatever the rasteriser reads
(`0x172..0x17e`, `docs/parhelia-block-state-map.md`).  The pass-through
program reads no constants.
