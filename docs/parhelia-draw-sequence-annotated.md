# One Parhelia-512 draw, annotated bit by bit

Every dword the vendor stack put on the bus between two consecutive triangles,
decoded in execution order. The point of this file is not to summarise the
protocol — `docs/parhelia-3d-integrated.md` does that — but to make it possible
to look at a real per-draw sequence and say, for each register write, either
"this is what that bit means and here is the document that says so" or
"we do not know".

Everything below is generated by `tools/annotate-stream.py`; nothing is
hand-edited.

```sh
tools/annotate-stream.py            # the annotated listing (§4)
tools/annotate-stream.py --coverage # the coverage table and unknown list (§5, §6)
tools/annotate-stream.py --all      # the whole captured ring
tools/annotate-stream.py --span 3   # an earlier draw-to-draw span
tools/annotate-stream.py --capture DIR   # a capture other than the default
```

Tags: **[HW]** measured on the board, **[BIN]** read from a vendor binary,
**[INF]** inferred, **UNKNOWN** not established anywhere.

**Exact input.** This listing was produced from the *committed* state of the
capture, because the working copy of `captures/live-ring-0528/` was being
rewritten by a concurrent capture run while this was written (its `secs2.txt`
had already been replaced by sections belonging to a different ring, so
`ringall2.txt` and `secs2.txt` on disk did not match each other). To reproduce
byte for byte:

```sh
mkdir -p /tmp/cap
for f in ringall2 secs2 calls2; do
    git show HEAD:captures/live-ring-0528/$f.txt > /tmp/cap/$f.txt
done
cp -r captures/live-ring-0528/warp-programs /tmp/cap/
tools/annotate-stream.py --capture /tmp/cap
```

The same sequence was also decoded from the working copy earlier in the day,
before it was rewritten. The two are different boots — different bus
addresses, different WARP heap, different fence serials — and the annotated
listings are **identical line for line apart from those addresses**: same 712
register writes, same 113 registers, same packet structure. The per-draw
sequence is deterministic.

## 1. The material and how the span was chosen

`captures/live-ring-0528/` is a dump taken from RAM on a live 0x0528 board
with the vendor X driver and a vendor GL client running:

| file | contents |
|---|---|
| `ringall2.txt` | the primary ring, one dword per line, 6144 dwords |
| `calls2.txt` | the 243 `(START, END)` operand pairs of the secondary calls |
| `secs2.txt` | the 243 secondary sections, dumped by address range |
| `warp-programs/entries.txt`, `slot-*.txt` | the live WARP program heap |

The annotator walks the primary ring, and every time a ring packet writes
`0x10a0`/`0x10a4` it splices the called section in at that point. A section
dump may have been read through a different mapping than the ring, so the tool
detects the constant address delta itself — a candidate delta has to map a
call's START *and* its END onto the same section, which makes a false positive
essentially impossible. (It is 0 for the committed capture and `0x400000` for
the working copy that was decoded first.)

Seven draw packets (`0x97080001`) appear in the capture, at ring packets
175, 360, 545, 730, 915, 1100 and 1285 — **exactly 185 packets and 416 ring
dwords apart**, so the per-draw sequence is strictly periodic and one period
is self-contained. This file annotates the last period: **ring packets 1100
through 1285**, i.e. from the sixth draw through the seventh.

That span contains

* 186 ring packets, of which **32 are secondary calls** carrying 1044 section
  dwords,
* 110 register-list packets (`opcode 0x00`), 10 block loads (`0x41`) and
  2 draws (`0x97`),
* **712 register writes** in **113 distinct registers**.

Every packet in the span frames exactly — the annotator reports a framing
break if a header's `totalDwords` does not land on the next header, and there
are none. Every called section in the span is present in the dump.

## 2. Framing — one correction to the established model

The rules in `docs/parhelia-3d-integrated.md` §2 all hold:

* packet header = `(opcode<<24) | (count<<17) | ((totalDwords-2) & 0xffff)`
* opcode `0x00` = register list, `[hdr][tag][data…][tag][data…]`, a tag packs
  four register indices LSB byte first, `reg = 0x1000 + idx*4`
* the primary ring is header-less: bare `[tag][data…]`
* a call is `0x20292820, 0, START|st, END|et, 0`, and `START & 3` selects the
  called section's framing (`2` = header-ful, `0` = header-less)

One rule needed correcting to make the capture frame at all:

> **index `0x21` terminates the current tag dword, not the packet.** The
> remaining index slots in that dword are skipped and consume no data; parsing
> continues with the *next* dword as a new tag, and the packet ends where its
> header says it ends.

Reading `0x21` as "end of packet" throws away the second half of every
multi-tag packet. The WARP stage-entry packet is the clearest witness:

```
00000009 212121dd 00000000 4c3c3c3c 20000002 20000002 00000002 0200300c
         21215147 00000fdb 00000000
```

`totalDwords` = 11. The first tag names only `0xdd` and then ends; the packet
continues with `4c3c3c3c` (four more registers) and `21215147` (two more), and
the eleventh dword is the last. Under the "0x21 ends the packet" reading the
packet would be three dwords long and the next eight would be garbage. With
the corrected rule the whole 1044-dword span frames with no leftovers.

`0x20` (PAD, `0x1080`) does consume a data dword, and discards it.

## 3. What the sequence actually is

Read as a whole, one period of this stream is a **flat/Gouraud triangle into a
320×240 window on a 1920×1200 32-bpp desktop**, with the X server's own 2D
fills interleaved into the same ring:

| phase | what it does |
|---|---|
| draw of the previous period | `0x97080001`, 3 vertices × 20 bytes |
| fence write-back | `0x1094` = serial, `0x1090` = write-back bus address |
| sync / flush | `0x1300 = 0x307`/`0x407`/`0x707` + a `0x12bc` tag pair |
| priming pseudo-draws | `0x1300 = 0x001000f4` twice and `0x005000f5` four times, each followed by the four texture units and (for four of the six) the legacy `0x1160-0x1198` DDA attribute planes — the one-pixel legacy draw the kernel replays every frame |
| 2D blits / fills | five `0x138c` LEN writes: 1920×1200 twice, 32×32 twice, 320×240 once — the X server, not the GL client |
| raster / ROP state | scissor `0..(320,240)`, blend off, alpha test off, depth test off + depth write off, fog off, z limits, PLNWT |
| vertex-fetch preamble | `0x1000 = 0`, `0x1040 = 4`, `0x10b0 = 0x0002305c` (triangle list), `0x10b4 = 0`, `0x10b8 = 0x83c00000` |
| WARP binds + block loads | four `0x1374/0x10f0/0x10f0/0x1100` bind packets, each followed by an `0x41` payload; then the five stage entries |
| vertex format | `0x1120-0x112c`, `0x1110/0x1114/0x1118`, `0x1130`, `0x111c`, `0x1144` |
| vertex fetch setup | `0x10b0 = 0x0006305c`, the eight stream bases, the four stride pairs, `0x1064 = 0`, `0x1060 = 0x280cc`, then the `0x10b8` attribute descriptors `0x20c00000`, `0xa1c50020`, `0`, `0` |
| render-target bind | slot 0 = colour, pitch 1920 ARGB8888; slot 1 = the depth surface, pitch 1920 format 0x36; slot 2 unbound |
| draw arm | `0x1300 = 0x707` + tag pair, `0x12b0 = 0x3fff8842`, `0x1300 = 0x00a60ec4`, `0x12f4 = 32.0` |
| texture / combiner | all four units `0x1200 = 0x0001000f, 0, 0, 0` (no texture); combiner slot 0 `MOV r0, v0` saturating in both the RGB and the alpha half; pads in slots 2, 4, 8, 10 |
| fence + last preamble | `0x1094` = next serial, then `0x1000 = 3`, `0x1040 = 4` |
| draw | `0x97080001 <start> <end>` — 5 dwords per vertex, 60 bytes, 3 vertices |

Three things fall straight out of the decode and are worth having in writing.

**The WARP constants are the projection and the viewport.** Block load
`41100023` writes constant slots 0-7 with a matrix whose diagonal is
`2/320 = 0.00625` and `2/240 = 0.008333` — the exact reciprocal of the scissor
rectangle `0x132c = 0x00f00140` (240 × 320). Block load `4104000b` writes
slots `0x160`/`0x161` with `(160, -120, 0.5, 1)` and `(160, 120, 0.5, 240)`,
i.e. the viewport scale/bias pair for the same window. This is the first
direct confirmation of what the `c[b1+0]` / `c[b1+8]` tail of the vendor
vertex program (`3d-integrated` §6) reads.

**The WARP entry arithmetic checks out to the dword, twice over.**
`entry -> bus = (v & ~3) * 3`, slots are `0x600` apart, and a program entry is
instruction index 96. The left-hand slot column below is looked up in
`warp-programs/entries.txt`; the right-hand one is derived from the index-96
rule applied to the primary entry alone. They agree everywhere, and the two
stage entries land on indices **111 and 115** — the numbers `3d-integrated` §8
records as the correction to an earlier "15/19":

**The two `0x41` packets with no descriptor quad carry WARP entry pointers.**
Eight of the ten block loads in the span carry `mtx1342`'s
`{n, first_slot, 1, 0}` descriptor and decode cleanly into constant-file
slots. The other two do not — and resolving their payload dwords against
`warp-programs/entries.txt` shows three of the four non-float words in the
first, and one in the second, are **valid WARP entries into real heap slots**:

```
0x41 BLOCK LOAD  hdr=41020007  count=1 (2 quads, 8 dwords)
  +0   03800015 00000000 3f800000 07956183
  +4   3f803f80 07955583 ffffffff 07956b83
  body[3] = 07956183 is a WARP entry: heap slot 0x16c02000, instruction index 96
  body[5] = 07955583 is a WARP entry: heap slot 0x16bffc00, instruction index 96
  body[7] = 07956b83 is a WARP entry: heap slot 0x16c03e00, instruction index 96

0x41 BLOCK LOAD  hdr=4106000f  count=3 (4 quads, 16 dwords)
  +0   000000e0 00000160 00000080 00000800
  +4   00000000 00000001 00000002 00000003
  +8   02003004 0200300c 00000000 00000000
  +12  07955583 ffffffff ffffffff ffffffff
  body[12] = 07955583 is a WARP entry: heap slot 0x16bffc00, instruction index 96
```

So the "preformatted body" form of opcode `0x41` (`opcode-41.md` §2,
`mtx1814`/`mtx1185`) is not opaque payload: it is a **table of program
entries** plus what look like pipeline words (`0x02003004`, `0x0200300c` are
`0x1130`-shaped, and `0x0200300c` is literally the value written to `0x1130`
later in the same section) and slot indices (`0x160`, `0x80`, `0x800`,
`0, 1, 2, 3`). Decoding this table is the single most valuable remaining
target in the per-draw stream, because it is the mechanism by which the vendor
binds a *set* of programs rather than one.

### The short list, in the order worth attacking

1. **The preformatted `0x41` body** (§3). Structure partly readable now — a
   program-entry table — but the field layout is UNKNOWN, and it is the only
   part of the per-draw stream whose *shape*, not just whose bit meanings, is
   undecoded.
2. **`0x1130` WARP pipeline control** (4 writes, three distinct values
   `0x0700300c`, `0x0200300c`, `0x00002204`). Written once per WARP bind and
   once per priming draw; the only established fact about it is a negative
   ("bit 9 is not a WARP bypass"). Nothing else about the WARP pipeline
   configuration is reachable without it. Note that the two per-draw values
   have **bit 9 clear**, contradicting `3d-submission-audit` A.5's
   `S[0x5f0] | 0x200` — see §7.
3. **`0x1110` / `0x1114` / `0x1118` vertex-attribute format**
   (`0x00000003`, `0x00287210`, `0x00006543` for this 5-float vertex;
   `0x00000f27`, `0x00287210`, `0x00006543` during priming). `warp-binding`
   names them and gives the kernel state offsets they come from, and
   `pixel-pipeline` §5.3 says the *texcoord* path is selected by these words
   rather than by microcode — but no bit is decoded. Two nibble-list-looking
   patterns are visible (`0x6543`, `0x7210`) and that is as far as inspection
   goes.
4. **`0x10f0` WARP MODE low bits.** `[3:0]` is a mode selector, `8` on the
   bind-and-run path and `2` on the stage-entry path here; **bit 5 is set in
   every `0x20000028`** and is accounted for by nothing.
5. **`0x12b0`** (`0x3fff8842` per draw, `0x3fff8000` at arm). Both values are
   traced to vendor code, no bit has a meaning.
6. **`0x12fc` raster mode** — bits `[4:0]` are identified; the captured value
   `0x0bb80024` has `0x5dc001` above them, i.e. 21 undecoded bits in the
   register that carries cull mode.
7. **`0x12f8`** `0x007fe000` per draw / `0x02800000` at init — named
   `reg3DThresholdAA` in the vendor parameter set, no field decoded.
8. **`0x111c`** (`0x00000fdb` per draw), **`0x1144`** (`0`), **`0x1378`**
   (`0`), **`0x12b8`** (`0x00070601`) — named or captured constants with no
   decoded content.
9. **`0x11c8` / `0x11d4` / `0x11d8`** — always 0 in every vendor path, so
   cheap to replay and impossible to learn anything about from a capture.
10. **`0x1160-0x1198` legacy DDA planes** (70 writes, the largest single block
    of partially-understood traffic). These are *not* the WARP vertex path;
    they belong to the two priming pseudo-draws. Their per-register roles come
    from `gl-driver`, which the live capture has already contradicted once.

### Payload fields, not registers

* **`0x10b8` attribute descriptor field `A`** — see §7; the wire value and the
  documented value disagree.
* **`B` (type) and `D`** in the same descriptor: `B = 2` and `D = 4` on the
  colour attribute, with no enumeration of either field anywhere.
* **The vertex bytes themselves are not in this capture.** The draw's operands
  fall in the gap between two called ranges, and only called ranges were
  dumped. So the 60 bytes that are the actual triangle are the one thing this
  file cannot show. A capture that also dumps `[END of previous call, START of
  the draw's operands)` would close that.

## 8. Confidence

The framing, the execution order and the register *addresses* are direct
readings of the capture and are not in doubt — the whole span frames to the
dword with no leftovers, on two independent boots. The register *meanings* are
only as good as the documents cited in each row of §5, which are themselves a
mix of `[BIN]` disassembly reading and `[HW]` measurement; this file adds no
new interpretation of its own except the eight conflicts in §7 and the three
findings in §3, all of which are arithmetic on the captured dwords or
lookups in the captured WARP heap.
